    对照 Codex：coderagent 还差什么

    这份文档把 coderagent 和 OpenAI Codex CLI 放在一起比，列出还值得改进的地方， 每一条都指到 coderagent 的具体文件，并标注工作量。

    它不是路线图，也不是许愿单——是一次对照审计的结论：2026-11-16 读完 Codex 的 文档（sandbox / approval / 命令集 / 多模态那几页）和 coderagent 的源码之后， 把两边摆在一起得出的差集。

    相关文档：主架构（能力差距矩阵那一节是本文的来源）、 设计逻辑、答问录。

    1. 一句话结论

    coderagent 的「内核」比 Codex 强（事件日志、信任边界、离线评测、网页版）， 「外壳」比 Codex 弱（沙箱隔离、命令覆盖面、界面细节）。

    Codex 赢在工程化的外壳：OS 级沙箱、网络开关、四十多条 slash 命令、图像/音频输入、 可调整的分栏 UI、终端通知。coderagent 赢在内核的可审计性：所有副作用过同一道闸、 项目配置只能拿走能力不能给能力、事件日志是唯一事实来源、有一套能跑指纹对比的离线评测。

    所以这份清单里，真正该抄的是安全边界和输入通道（P0 的 1、3、4、5 和 P1 的 1、2）， 其余多半是「有了更好」而不是「缺了就危险」。

    进度：§8 的第 1～10 步都做完了（两个 bug、网络开关、/review、reasoning_effort、 TUI 小件、死配置清理、OS 级沙箱、图片输入 + 中断粒度 + Markdown、 apply_patch + TUI 文件树 + P2 清理一批、OTel exporter + 第二轮对照的差距）。 做完的条目在小节标题上标着「✅ 已修」，原样保留着原来的描述，好回头看差在哪。

    2. 怎么读这份清单

    级别 含义
    P0 缺了会不安全或者会出错，先做
    P1 缺了明显不好用，影响日常效率
    P2 缺了锦上添花，或者只是清理（死配置、无效代码）

    工作量的口径：一个「小」= 半天以内，一个「中」= 一到三天，一个「大」= 一周以上。

    3. P0：先做

    3.1 没有 OS 级沙箱，网络也没有开关 ✅ 已修

    现状：sandbox.type 默认 local（src/coderagent/config/defaults.yaml:62）， 走 build_environment() → CodingEnvironment（src/coderagent/core/sandbox.py:26-29）， 命令用 subprocess 以用户本人的身份跑。想隔离只能整个换环境：

    sandbox:
  type: swerex_docker   # 或 bubblewrap / contree / modal

    但这条路是全有全无的：要么整个 agent 在容器里，要么全在宿主上。Codex 的模型是 两个正交的轴——sandbox_mode（read-only / workspace-write / danger-full-access） × approval_policy（on-request / on-failure / never），而且沙箱是操作系统级别的：

    平台 Codex 的隔离手段
    macOS Seatbelt (sandbox-exec)
    Linux bubblewrap + seccomp + Landlock
    Windows 原生 sandbox

    而且 Codex 默认断网，agent 想联网得显式开。

    coderagent 现状：

    • ~~没有操作系统级的文件/进程约束，local 就是裸的 subprocess；~~ ✅ 已修
    • curl / wget / nc 这些出网命令，在 src/coderagent/tools/bash_policy.py:90-96 里被标成「危险」，但危险只意味着弹审批框，不意味着拦下来—— default 模式下用户一路点「允许」就能把数据发出去；
    • ~~没有 sandbox_policy.network_access 这样的开关。~~ ✅ 已修（见下面「已修」）

    影响：~~一个被 prompt injection 拐走的 agent，在 local 模式下能读 ~/.ssh、 能改 ~/.zshrc、能把仓库内容 POST 到外面。permissions.include_dirs 只能加目录， 没有「只允许写这些目录」的方向。~~ ✅ 已修（网络开关 + OS 级沙箱）

    建议：

    1. ~~先做便宜的半个——加一个 network: deny | allow 开关，在 bash_policy 里把 出网命令从「弹审批」升级成「直接拒绝」。~~ ✅ 已修（见下面）
    2. ~~再做 sandbox_mode 三档，把 local 拆成 read-only / workspace-write / full-access，其中 workspace-write 在 macOS 上接 Seatbelt、Linux 上接 bubblewrap。~~ ✅ 已修（见下面）

    已修：网络开关（permissions.network，默认 allow）

    • bash_policy.py 里加了一张出网命令的表（NETWORK_COMMANDS）和 git 的出网子命令 （NETWORK_SUBCOMMANDS），另有一个 needs_network() 判断某一段命令要不要出网；
    • PermissionPolicy 多了一个 network 参数：deny 时，出网的命令直接拒绝， 不是弹审批框；
    • 拒绝在所有模式下都成立，bypass 也不例外——这一点和原文写的 「（bypass 模式除外）」不同：磁盘边界（within_bounds()）本来就在 bypass 下成立，Codex 的 network_access 也和 approval_policy 是两个正交的轴， 所以让网络边界跟磁盘边界一个口径；
    • 用户写的 allow 规则放宽不了它，和路径边界一个待遇；
    • 模型会被告知：一段 <permission_network policy="deny"> 进上下文，和 <permission_mode ...> 一样，每轮重算，不烤进 system prompt；
    • 信任边界照旧：项目里的配置只能关网络，不能开网络（core/trust.py 的 tightened() 把 network 留在配置里当且仅当它是 deny；config/loader.py 里项目层说 deny 时，用户层不能把它重新打开）。

    已修：OS 级沙箱（sandbox.mode，默认 full-access）

    • 新模块 src/coderagent/core/os_sandbox.py：三档 read-only / workspace-write / full-access，由操作系统来执行——macOS 是 Seatbelt（sandbox-exec）， Linux 是 bubblewrap（bwrap）。越界的命令是被内核挡下来的，不是被文件里的 一条规则挡下来的；
    • 配置上就是 sandbox.mode，只对本地沙箱有意义：
    sandbox:
  type: local
  mode: workspace-write
    • 命令是被包起来送进沙箱的（<tool> … /bin/sh -c '<整条命令>'）：整条命令作为 一个参数进去，所以解析管道的那个 shell 也在沙箱里——否则管道会有一半漏在外面；
    • 约束的是 agent，不是用户：围栏挂在 ToolContext.sandbox 上，只由 bash 工具 的命令用。校验命令是用户自己的命令，按用户的身份跑，在沙箱外面；
    • read-only 连写文件的工具一起拒（write、edit、multi_edit）：它们写的是 用户机器上的文件，在沙箱外面，用户写的 allow 规则也放宽不了；
    • 路径边界没有被绕开：within_bounds() 在所有模式下都生效，还是用户的 allow 规则放宽不了——这一点在原文里被点名过，实现时照做了；
    • 闸和沙箱是两层，不是二选一：bypass 跳过的是审批提问，不是磁盘边界；
    • 可写的目录：工作目录 + permissions.include_dirs + 系统的临时目录（构建总得 有地方放东西），read-only 只留临时目录；
    • 网络在操作系统那一层也关着：permissions.network: deny 时，Seatbelt 加 (deny network*)，bubblewrap 加 --unshare-net；
    • 信任边界照旧：项目里的配置只能关沙箱，不能开沙箱（core/trust.py 的 tightened() 只留下更紧的那两档；config/loader.py 里两档里更紧的算数， 用户层不能把项目关掉的沙箱重新打开）；
    • 项目不能决定命令在哪里跑：沙箱的 type 和环境的那些选项（image 等等） 都从项目层丢掉——tightened() 只留下 mode（core/trust.py）。项目的环境会 把用户的工作目录一起带走，那个选择归用户；
    • 模型会被告知：一段 <sandbox mode="…"> 进上下文，每轮重算，不烤进 system prompt；
    • 机器上缺那个程序，会话就起不来（UnsupportedSandbox）：承诺兑现不了，就不要许。

    注意：within_bounds()（src/coderagent/tools/permissions.py）在所有模式下都生效， 用户写的 allow 规则放宽不了这个边界——这是 coderagent 比 Codex 强的地方， 做 OS 级沙箱时不要把它绕开——没有绕开：sandbox.mode 的每一档都跑在 within_bounds() 后面，用户规则放宽不了它。

    3.2 没有 /review ✅ 已修

    原来：coderagent 的命令注册表在 src/coderagent/ui/commands/builtin.py， 二十来条命令里没有 review。Codex 有 /review，能把当前分支的改动拉出来做一次 专门的审查轮。

    影响：审查这件事只能靠用户自己在输入框里写「帮我 review 一下这些改动」， 走的是普通对话路径——没有独立的提示词、没有独立的 diff 上下文。

    已修：一条 /review [范围] 命令（src/coderagent/ui/commands/review.py）

    • 不带范围时审查工作树的改动（git diff HEAD，没有提交时退回 git diff）； 带范围时审查那个范围（git diff main..HEAD）；
    • 范围 git 不认时说一句「Git does not know …」，不静默；
    • 新增但还没进版本库的文件单独列出来（git status --porcelain），它们不在 diff 里， 提示词里点名，模型自己去读；
    • diff 进的是一次专门的审查轮的提示词（REVIEW_PROMPT），提示词里明写 「Do not change any file: this is a review, not a fix」—— 审查只出结论，不动代码（要改的话走正常的审批门）；
    • diff 超过 60000 字符会被截断，并告诉模型「the diff is cut here, read the files yourself」；
    • 审查轮在当前会话里跑，结果留在对话里，用户可以接着说「把第二条改掉」；
    • diff 只在这一轮里：轮结束就换成一句提示（「改动不在上下文里了，自己再读一遍」）， 否则一次大审查就把整个会话的窗口吃掉了。

    实现要点：命令自己不跑模型，它把提示词交给界面的 submit 回调—— CommandContext 多了一个 submit 字段（TUI → 工作线程，网页版 → 会话线程， CLI → render(loop.run_turn(...))）。界面不能跑轮时（submit is None）说一句 「This interface cannot run a turn, so it cannot review.」就完了。 没有另起一个子 agent：审查留在对话里，用户能直接接着用结论。

    3.3 没有 reasoning_effort（思考预算） ✅ 已修

    原来：src/coderagent/config/schema.py 的 ModelConfig 里没有 reasoning_effort 这个字段（grep 全仓为零）。传给 litellm 的是 model_kwargs 的其余部分，所以理论上 用户可以自己在 model_kwargs 里塞 reasoning_effort: high——但没有开关、没有校验、 没有文档、没有界面，而且各个厂商对这个参数的叫法不一样（OpenAI 是 reasoning_effort，Anthropic 是 thinking.budget_tokens，DeepSeek 是别的）。

    影响：想省钱的用户没法「这个任务认真想」，想快点的用户也没法「别想了」。 model.routing 和 model.routing_rules（按用途选模型）能解决一部分， 但「同一个模型、不同的思考量」这个维度是空的。

    已修：一个 model.reasoning_effort 字段

    • 配置里写 model.reasoning_effort: high，取值是 minimal / low / medium / high， 留空 = 模型的默认。写错在加载配置时就被拒（pydantic 的字段校验器）， 不用等到发请求才炸。
    • 翻译在一处做：src/coderagent/models/reasoning.py 的 translate(model_name, effort)。 OpenAI 这一家原样传 reasoning_effort；Anthropic 这一家换成 thinking: {type: enabled, budget_tokens: N}（N = 1024 / 2048 / 8192 / 16384， Anthropic 至少要 1024 个 token，所以 minimal 就是 1024）。
    • 翻译发生在 LiteLLMBackend 里面，在别名解析之后——litellm_config 里的别名 指向的是哪个模型，就按那个模型的厂商来翻译。
    • 用户自己在 model_kwargs 里写的同一个参数优先（setdefault）， 想手工调 token 数的人不受打扰。
    • 因为翻译在 backend 里，每一处建 backend 的地方都白拿：主模型、model.routing 的子模型、/model 换模型、网页版的连接测试、自定义命令。
    • 界面上也有：网页版设置页的模型表单里多了一个「思考预算」下拉框； /model 会把当前的档位打印出来，换模型时带着走。

    3.4 真 bug：~/.coderagent/CLAUDE.md 被加载了两次 ✅ 已修

    原来：

    • src/coderagent/core/instructions.py:66 — load_instructions() 读 home / USER_FILE，USER_FILE = "CLAUDE.md"（instructions.py:12）， 于是读的是 ~/.coderagent/CLAUDE.md；
    • src/coderagent/core/memory.py:36 — load_user_memory() 读 home / Path(config.user_path).name，而 user_path 的默认值就是 ~/.coderagent/CLAUDE.md（src/coderagent/config/schema.py:108）；
    • 这两块在 src/coderagent/core/context.py:270-293 被同时拼进指令段。

    影响：用户级的 CLAUDE.md 每次组消息都出现两遍，白烧 token； 更要紧的是，如果用户在这份文件里写了「每次回答都要先说 X」这类自我约束， 模型看到的是两遍，可能误以为那是强调。

    怎么修的：core/instructions.py 加了 once_per_file()，组消息的时候 一个文件只出一段，后读的盖住先读的。记忆那份赢——它每轮重读， 所以 /memory confirm 写下的偏好在下一轮就生效，不用等下一个会话。

    3.5 真 bug：MCP 的 url 和 headers 配了但不生效 ✅ 已修

    一、span 算对了

    • OtlpExporter 走 OTLP/HTTP（JSON），发到 telemetry.otel_endpoint； telemetry.otel_headers 是给那些要 key 的后端用的。

    • 事件日志仍然是唯一的事实：追踪是从日志算出来的，日志照写不误。
    • 手动发：coder export --format otel --push 把一个会话推到配置的地址上。
    • 信任边界：追踪里是 agent 读过的东西，项目不能把它送到自己的地址 （core/trust.py 的 tightened() 只留下「关掉」那一种，项目带的 header 也丢掉）； 用户也不能把项目关掉的追踪重新打开（config/loader.py）。 「追踪发到哪里」是用户的决定，不是克隆下来的仓库的决定。

    把 trace 交给云端 coderagent 的事件日志在本地，评测能离线跑——这是它最值钱的地方，别动

    9.1 命名 profile ✅ 已修

    怎么做的：

    • 配置里多了一张表：profiles: {名字: {一截配置}}，选中哪个由 profile: 说了算， 命令行上也可以 --profile（短写 -p）。
    • profile 压在用户配置上面，和 -c 一样是「临时的覆盖」； 项目的收紧仍然压在最上面——profile 不能把项目关掉的沙箱和网络再打开。
    • 项目不许定义 profile，也不许选 profile：core/trust.py 把项目层里的 profile 和 profiles 丢掉。理由和 5.6 一样——选哪套权限是用户的决定， 克隆下来的仓库不能替用户挑一套宽松的。

    9.2 结构化输出 ✅ 已修

    怎么做的：

    • --output-schema <文件>：最后一条回答必须是符合这个 schema 的 JSON。 合上的答案放在这一轮 JSON 的 output 字段里。
    • schema 也给模型看：系统提示词后面附上一段 <output_schema>，说清「只答 JSON，不要散文」。
    • 不合格就再来一次：回答不是合法 JSON、或者对不上 schema， 把错在哪儿写回去让模型改，最多两次（第二次还不对就以 schema_invalid 停下）。
    • 不引依赖：仓库里没有 jsonschema，所以校验器是自己写的 （core/schema.py，认 type / properties / required / additionalProperties / items / enum / nullable 这几样）。这是刻意的：为了一个功能装一个包不划算。
    • Codex 是靠模型服务端约束的，coderagent 走的是 litellm，好几个 provider 不认那个参数， 所以这边是「提示 + 校验 + 重试」。慢一点，但每个 provider 都一样。

    9.3 MCP 服务器的工具过滤 ✅ 已修

    怎么做的：enabled_tools（只露这些）和 disabled_tools（这些不露）， 两个都能按名字筛一个服务器的工具，* 表示全部。 过滤只减不增：enabled_tools 空着就是全给，disabled_tools 里的名字一定不露。

    9.4 @文件 的内容进消息 ✅ 已修

    怎么做的：

    • 提问里的 @路径（终端界面和命令行里都直接写）和 /mention <文件> 都会把 文件的内容带进消息，模型不用自己再花一次工具调用去读。
    • 不是文件的名字就当没写：@ 还有别的用处（邮箱、装饰器）， 所以只有真的存在的文件才会被打开（core/mentions.py）。
    • 守路径边界：工作目录外面的文件、被 deny_paths 挡住的文件不带， 消息里写明「这个文件不让看」，而不是把内容偷偷塞进去。
    • 只带文本：不是文本的文件只被点名；图片走 /image，不在这里重复一套。 超过 20000 字符的文件会截断，并且说明截断了。

    • shell_environment（安全向）：命令的环境里像秘密的名字一定被去掉 （*_API_KEY、*_KEY、*_TOKEN、*_SECRET、*_PASSWORD、*_PASSWD、 *_CREDENTIALS、*_ACCESS_KEY），除非用户用 include 一个一个地放回来。 三个档位：all（除了秘密）、core（只有命令要的那些）、none（什么都没有）。 项目只能藏更多，不能把用户藏的放出来（core/trust.py 丢掉项目的 include）。
    • tools.max_output_tokens（默认 8000）：每一个工具的结果都裁，不只是 bash。 裁的时候留头和尾，中间写明裁掉了什么；完整的结果还留在事件日志里。

    9.8 第 12 步：会话的生命周期和历史的保留 ✅ 已修

    怎么做的：

    • ui.file_opener + /open <路径>：vscode、cursor、windsurf 是认得的名字， 也可以是用户自己的命令（my-editor {file} --wait）。文件得在工作目录里面 （走 within_bounds），不然 /open 会说它在边界外。 项目不能挑编辑器——那个程序跑在用户的机器上，core/trust.py 把项目层的 ui.file_opener 丢掉。
    • supports_parallel_tool_calls（mcp.servers[] 上，默认 true）： 一轮里模型可以同时调两个工具，MCP 的工具本来就在线程池里跑。 所以这个开关不是「要不要并行」，而是「这个服务器扛不扛得住两个调用」： 设成 false，这个服务器的调用彼此排队，别的服务器照旧并行。
    • /rename / /archive / /delete：名字和「收起来了」这两个状态 写在事件日志里（STATE_CHANGE 事件），和「事件是唯一的事实」这条一致—— 会话靠重放日志重建，重建出来的名字和归档状态也是对的。 收起来的会话不在 /resume 的列表里，但还在盘上；/archive 再跑一次就拿出来。 /delete 要 id，而且不删你正待着的那个会话。
    • history.persistence / history.max_bytes：save-none 让会话只活在内存里 （盘上什么都不写）；save-none 之外的默认值是 save-all。 max_bytes 是全部会话的历史能占的字节数，超了就从最老的开始删， 正在跑的那个会话永远不在被删的里头。

    9.9 第 13 步：一份总结，和一段岔开的对话 ✅ 已修

    怎么做的：

    • /recap（只总结，不动上下文）：复用压缩的那套摘要机器（core/context.py 的 recap()），但不碰 self.summaries，不碰历史，也不把摘要交给模型—— 模型看到的还是整段对话。摘要只是给你看的一份报告，不是干活的一步。
    • 摘要的钱记在会话上：摘要用 context.summarize_model 跑（没配就是会话自己的模型）， 费用记到 session.total_cost，事件日志里是一条 RECAP 事件（带 summary / text / cost）。 collect() 按用途 recap 归集，所以 /cost 里看得见这一笔。
    • /side <问题>（岔出去聊一条）：当前会话分叉成一个新会话（SessionStore.side()）， 新会话知道自己的父亲（metadata["parent"]），原来的会话一个字都没动。
    • 跑完就回来：AgentLoop.run_turn(..., session=...) 会切到岔开的会话跑那一轮， 然后切回来（switch_to(..., start=False)，所以 SessionStart 的 hook 不会响两次）。 问题和回答记在你当前会话的日志里（一条 SIDE_CONVERSATION 事件）， 所以 agent 不会丢掉干活的线索——但也就这些：岔开的那些消息留在岔开的会话里， 它用的工具也算在那个会话上。
    • 岔开的会话有自己的 id，跟别的会话一样能打开（/resume <id>）。
    • 顺带修了一个真 bug：工具和检查点原来是在 build 的时候把会话钉死的 （run.py），所以 /resume、/fork、/clear 之后，工具的结果落进了旧会话的日志。 现在工具的上下文、checkpoint 的回调、子 agent 的 session_id 都跟着循环所在的会话走。
