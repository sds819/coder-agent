    对照 Codex：coderagent 还差什么

    这份文档把 coderagent 和 OpenAI Codex CLI 放在一起比，列出还值得改进的地方， 每一条都指到 coderagent 的具体文件，并标注工作量。

    它不是路线图，也不是许愿单——是一次对照审计的结论：2026-11-16 读完 Codex 的 文档（sandbox / approval / 命令集 / 多模态那几页）和 coderagent 的源码之后， 把两边摆在一起得出的差集。

    相关文档：主架构（能力差距矩阵那一节是本文的来源）、 设计逻辑、答问录。

    1. 一句话结论

    coderagent 的「内核」比 Codex 强（事件日志、信任边界、离线评测、网页版）， 「外壳」比 Codex 弱（沙箱隔离、命令覆盖面、界面细节）。

    Codex 赢在工程化的外壳：OS 级沙箱、网络开关、四十多条 slash 命令、图像/音频输入、 可调整的分栏 UI、终端通知。coderagent 赢在内核的可审计性：所有副作用过同一道闸、 项目配置只能拿走能力不能给能力、事件日志是唯一事实来源、有一套能跑指纹对比的离线评测。

    所以这份清单里，真正该抄的是安全边界和输入通道（P0 的 1、3、4、5 和 P1 的 1、2）， 其余多半是「有了更好」而不是「缺了就危险」。

    2. 怎么读这份清单

    级别 含义
    P0 缺了会不安全或者会出错，先做
    P1 缺了明显不好用，影响日常效率
    P2 缺了锦上添花，或者只是清理（死配置、无效代码）

    工作量的口径：一个「小」= 半天以内，一个「中」= 一到三天，一个「大」= 一周以上。

    3. P0：先做

    3.1 没有 OS 级沙箱，网络也没有开关

    现状：sandbox.type 默认 local（src/coderagent/config/defaults.yaml:62）， 走 build_environment() → CodingEnvironment（src/coderagent/core/sandbox.py:26-29）， 命令用 subprocess 以用户本人的身份跑。想隔离只能整个换环境：

    sandbox:
  type: swerex_docker   # 或 bubblewrap / contree / modal

    但这条路是全有全无的：要么整个 agent 在容器里，要么全在宿主上。Codex 的模型是 两个正交的轴——sandbox_mode（read-only / workspace-write / danger-full-access） × approval_policy（on-request / on-failure / never），而且沙箱是操作系统级别的：

    平台 Codex 的隔离手段
    macOS Seatbelt (sandbox-exec)
    Linux bubblewrap + seccomp + Landlock
    Windows 原生 sandbox

    而且 Codex 默认断网，agent 想联网得显式开。

    coderagent 现状：

    • 没有操作系统级的文件/进程约束，local 就是裸的 subprocess；
    • curl / wget / nc 这些出网命令，在 src/coderagent/tools/bash_policy.py:90-96 里被标成「危险」，但危险只意味着弹审批框，不意味着拦下来—— default 模式下用户一路点「允许」就能把数据发出去；
    • 没有 sandbox_policy.network_access 这样的开关。

    影响：一个被 prompt injection 拐走的 agent，在 local 模式下能读 ~/.ssh、 能改 ~/.zshrc、能把仓库内容 POST 到外面。permissions.include_dirs 只能加目录， 没有「只允许写这些目录」的方向。

    建议：

    1. 先做便宜的半个——加一个 network: deny | allow 开关，在 bash_policy 里把 出网命令从「弹审批」升级成「直接拒绝」（bypass 模式除外）。一天内能做完，收益最大。
    2. 再做 sandbox_mode 三档，把 local 拆成 read-only / workspace-write / full-access，其中 workspace-write 在 macOS 上接 Seatbelt、Linux 上接 bubblewrap。 这是「大」的工作，但这是 Codex 真正拉开差距的地方。

    注意：within_bounds()（src/coderagent/tools/permissions.py）在所有模式下都生效， 用户写的 allow 规则放宽不了这个边界——这是 coderagent 比 Codex 强的地方， 做 OS 级沙箱时不要把它绕开。

    3.2 没有 /review

    现状：coderagent 的命令注册表在 src/coderagent/ui/commands/builtin.py:428-483， 一共二十来条，没有 review。Codex 有 /review，能把当前分支的改动拉出来做一次 专门的审查轮。

    影响：审查这件事现在只能靠用户自己在输入框里写「帮我 review 一下这些改动」， 走的是普通对话路径——没有独立的提示词、没有独立的 diff 上下文、也没有独立的结果区。

    建议：加一条 /review [范围] 命令，把工作树的 diff（或 base..head）作为上下文喂进去， 走一次专门的审查提示词。现有零件都有：/diff（builtin.py:446）已经会算工作树改动， src/coderagent/core/checkpoint.py 存着每一轮的快照。工作量：小到中。

    3.3 没有 reasoning_effort（思考预算）

    现状：src/coderagent/config/schema.py 的 ModelConfig 里没有 reasoning_effort 这个字段（grep 全仓为零）。传给 litellm 的是 model_kwargs 的其余部分，所以理论上 用户可以自己在 model_kwargs 里塞 reasoning_effort: high——但没有开关、没有校验、 没有文档、没有界面，而且各个厂商对这个参数的叫法不一样（OpenAI 是 reasoning_effort，Anthropic 是 thinking.budget_tokens，DeepSeek 是别的）。

    影响：想省钱的用户没法「这个任务认真想」，想快点的用户也没法「别想了」。 model.routing 和 model.routing_rules（按用途选模型）能解决一部分， 但「同一个模型、不同的思考量」这个维度是空的。

    建议：ModelConfig 加一个 reasoning_effort: str = ""，写进 model_kwargs 之前先按厂商前缀翻译成对应的参数名。工作量：小。

    3.4 真 bug：~/.coderagent/CLAUDE.md 被加载了两次

    现状：

    • src/coderagent/core/instructions.py:39 — load_instructions() 读 home / USER_FILE，USER_FILE = "CLAUDE.md"（instructions.py:13）， 于是读的是 ~/.coderagent/CLAUDE.md；
    • src/coderagent/core/memory.py:32 — load_user_memory() 读 home / Path(config.user_path).name，而 user_path 的默认值就是 ~/.coderagent/CLAUDE.md（src/coderagent/config/schema.py:108）；
    • 这两块在 src/coderagent/core/context.py:215-220 被同时拼进指令段。

    影响：用户级的 CLAUDE.md 每次组消息都出现两遍，白烧 token； 更要紧的是，如果用户在这份文件里写了「每次回答都要先说 X」这类自我约束， 模型看到的是两遍，可能误以为那是强调。

    建议：二选一——要么把用户级指令文件从「指令」和「记忆」里择一， 要么让 load_user_memory() 跳过已经被 load_instructions() 读过的那个路径。 工作量：极小（改一处 + 一个回归测试）。

    3.5 真 bug：MCP 的 url 和 headers 配了但不生效

    现状：src/coderagent/config/schema.py:117-124 的 MCPServerConfig 里有 url（http 传输的地址）和 headers 两个字段，文档里也写着它们能用。但是 src/coderagent/tools/mcp.py 里从头到尾没有出现过 url 或 headers—— MCPManager.start() 在 mcp.py:182 只认 server.command：

    if not server.enabled or not server.command:
    continue

    影响：配了 url: 的 MCP server 被静默跳过——不启动、不报错、不出现在 /mcp 的状态里。用户看 /mcp 只看到「没有连上的 server」，根本猜不到是配置字段没用。

    建议：要么实现 http 传输（streamable_http），要么在 schema 上拒收 url/headers 并给出明确报错（extra="forbid" + 迁移提示）。静默忽略是最糟的一种。 工作量：小（先做「拒收 + 报错」，实现 http 另算）。

    4. P1：影响日常效率

    # 差距 现状（指到文件） Codex 有 工作量
    4.1 没有图片/音频输入 消息只有文本：core/context.py 的 build_messages() 拼的是 {"role","content"} 字符串，没有多模态分支 /image 附件（0.167/0.168 起支持图像与音频） 中
    4.2 没有输入历史 TUI 的 Input 部件没有历史栈（src/coderagent/ui/tui.py 里没有相关实现），上下键只能移动光标 上下键翻历史 小
    4.3 回答不渲染 Markdown TUI 直接把原文塞进 Static（tui.py:197），代码块、表格、标题都是平的 富渲染 中
    4.4 中断的粒度是「轮」 loop.cancel 只在每轮模型调用之前检查（src/coderagent/core/loop.py:179-181），tools/executor.py 里没有取消检查——一条跑着的 bash 停不下来，只能等它自己结束 能中断正在跑的工具 中
    4.5 没有 @ 提及文件 输入框里 @foo.py 不会被展开成路径 @ 补全文件 小
    4.6 TUI 没有文件树 文件树只在网页版左栏（src/coderagent/web/）；终端里只能靠 ls 工具 侧栏文件树 中
    4.7 TUI 没有会话切换器 终端里切会话要 /resume（builtin.py:437），是一个列表文本 会话切换面板 小
    4.8 没有终端通知 跑完一轮没有任何通知；长任务跑完时人不在屏幕前就不知道 OSC 777 通知（可配） 小
    4.9 没有 apply_patch 工具 改文件用 write / edit / multi_edit（src/coderagent/tools/builtin/fs.py），是整串替换 apply_patch（带上下文的块补丁） 中

    关于 4.9 要说句公道话：edit 的 old_string 匹配逻辑（fs.py:36-58）已经处理了 CRLF 变体和「不唯一」的报错，可读性不错。apply_patch 的真正价值是模型侧更省 token （块补丁比整段内容短），不是功能更多。所以这条排 P1 而不是 P0。

    5. P2：清理与锦上添花

    5.1 死配置

    配置项 位置 现状
    ui.theme config/schema.py:152、config/defaults.yaml:57 全仓没有任何地方读它
    ui.show_reasoning config/schema.py:153、config/defaults.yaml:58 全仓没有任何地方读它
    model.max_retries config/schema.py:44 只有网页版服务器用（web/server.py:56 把它写进环境变量），终端里配了不生效

    ui.approval_timeout（schema.py:154）是好的——网页版在用。

    5.2 认证失败要重试十分钟

    src/coderagent/models/backends.py:31-39 的 abort_exceptions 里没有 litellm.exceptions.InternalServerError。中转站在完全没有 key 的时候返的是 500， 于是走满 10 次重试（约两分钟）才放弃；而 key 写错的时候返 AuthenticationError， 在列表里，立即失败。同一个错，两种体验。

    建议把 InternalServerError 加进 abort_exceptions，或者只在「明确是配额/限流」时重试。

    5.3 AGENTS.md 会话中途改了不生效

    src/coderagent/core/context.py:109-110 在 ContextEngine 构造时读一次指令文件， 之后只追加子目录的指令（context.py:392-395）。项目根目录的 AGENTS.md 在会话开始后被修改，模型这一轮还看的是旧内容。

    Codex 的做法是每次会话开始、每次 compact 之后重读。工作量：小（把「读指令」 挪到和记忆同一层的「每轮重算」里）。

    5.4 hook 事件只有 6 个

    现在有：PreToolUse、PostToolUse、UserPromptSubmit、Stop、SessionStart、SessionEnd （src/coderagent/tools/executor.py:104,169、src/coderagent/core/loop.py:145,364,372,376）。

    Codex 还提供压缩前后、通知、子 agent 停止等事件。PreCompact 对本项目特别有用—— 压缩是 coderagent 的核心机制之一（见上下文专题）， 压缩前后的钩子是天然的「记录摘要质量」的地方。

    5.5 自定义命令只有项目级，allowed-tools 太粗

    src/coderagent/ui/custom_commands.py:54 只从 <cwd>/.coderagent/commands 读， 没有用户级目录——用户没法给自己装一套全局命令。 allowed-tools 在 custom_commands.py:51 被 _split_tools 按 spec.split("(")[0] 截断，所以 bash(git diff:*) 里的参数模式整个丢掉，只剩工具名。

    5.6 OTel 只是本地 JSON

    src/coderagent/core/telemetry.py:119 的 otel() 返回一份 OTLP/JSON 的 dict， 没有 exporter，不往任何地方发。要接真正的 OTel 后端，还差一个 exporter。

    5.7 其它零碎

    • src/coderagent/core/instructions.py:12 的 PROJECT_FILES 常量定义了但没人用（死代码）。
    • 网页版的改动列表来自会话的检查点（api.py:175 的 /changes）， 没有检查点的改动不会出现在列表里（这条已经写进 docs/usage/coderagent_web.md 的「已知差距」）。

    6. coderagent 比 Codex 强的地方（不要照抄 Codex 时弄丢）

    能力 Codex coderagent
    信任边界 项目配置可以带 MCP server、hook 项目只能拿走能力，不能给能力（src/coderagent/core/trust.py）：模式只留 plan/readonly、规则只留 deny、路径取并集、工具取交集
    路径边界 由沙箱决定 within_bounds() 在所有模式下都生效，用户的 allow 规则也放宽不了
    事实来源 会话状态 事件日志是唯一事实来源，压缩只把原文移出窗口，不删事实
    离线评测 有 codex exec，但没有可对比的指纹 coder eval + coder eval-compare + 指纹，能测出「harness 坏了」（模型会绕开坏掉的 edit，只数工具调用是测不出来的）
    网页版 有 IDE 扩展，没有完整的网页终端 完整的网页版：SSE 流式、三栏、会话列表、设置页分层预览、审批卡片
    审批粒度 on-request / on-failure / never Always allow 会往 ~/.coderagent/rules.yaml 写规则，规则本身是文件、可读可改

    做 OS 级沙箱时最该小心的一件事：Codex 的 approval_policy=never 允许完全放开； coderagent 的 bypass 模式语义类似，但它建立在「所有副作用过同一道闸」之上。 加了沙箱之后，闸和沙箱是两层，不是二选一——bypass 应该绕过审批，不应该绕过路径边界。

    7. 不建议照抄 Codex 的地方

    Codex 的做法 为什么别抄
    approval_policy=never 一个人类完全不在场的档 coderagent 的 bypass 已经是这个东西，但它是显式选的；不要顺手给它一个默认值
    沙箱策略和审批策略绑在一起理解 Codex 已经拆成两个正交的轴了，这一条照抄是对的（见 3.1）
    把一切都做成 slash 命令 coderagent 的命令有 20 多条了，再加就要有 /help 的分类。Codex 的命令更多是因为它的用户群更杂
    把 trace 交给云端 coderagent 的事件日志在本地，评测能离线跑——这是它最值钱的地方，别动

    8. 建议的推进顺序

    顺序 做什么 为什么排这个位置
    1 修 3.4 + 3.5 两个 bug 都是几行的事，但一个白烧 token、一个静默吞配置
    2 加网络开关（3.1 的第一步） 一天内能做完，堵住最大的口子
    3 /review（3.2） 现有零件都齐了，性价比最高的功能缺口
    4 reasoning_effort（3.3） 便宜，且和 model.routing 是一套东西
    5 TUI 小件（4.2 / 4.5 / 4.7 / 4.8） 四个小改动合一个提交，都是「有了就顺手」
    6 死配置清理（5.1） 顺手做，别单开
    7 OS 级沙箱（3.1 的第二步） 最大的一件，做完前面再说
    8 图片输入（4.1）、中断粒度（4.4）、Markdown（4.3） 需要设计，不适合顺手做
